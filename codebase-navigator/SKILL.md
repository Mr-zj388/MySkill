# 代码导航

用中文维护一份能帮助后续开发者找到代码的地图。默认按模块索引，记录定位和修改所需的信息；具体实现以源码为准。

## 1. 确定范围

读取项目已有的 `AGENTS.md`、`CLAUDE.md` 和导航文档，沿用当前入口与目录约定。通过项目清单、源码入口和实际调用关系确认模块职责。

- **首次建立**：覆盖用户指定范围；未限定时先梳理顶层模块和关键入口，再按定位需要补充模块详情。
- **增量维护**：以用户指定的变更为范围，只更新受影响的导航。提交前检查暂存区；工作区检查同时考虑未暂存和未跟踪文件。没有 Git 时按指定路径核对源码。
- **仅查询代码位置或讨论方案**：给出定位结果或方案，不生成导航文件。

开始写入前简要说明本次覆盖的模块和拟更新的文档。范围以实际检查结果为准，未检查部分明确说明。

## 2. 按需组织导航

已有导航沿用现有结构；没有导航时采用以下最小结构：

| 位置 | 内容 |
| --- | --- |
| 项目已有的 `AGENTS.md` 或 `CLAUDE.md` | 添加一条导航入口及何时读取的说明，保留原有内容；两者均无时默认使用 `AGENTS.md` |
| `docs/ai-nav/_index.nav.md` | 模块职责、源码入口和相关文档的总索引，以及跨模块架构文档链接 |
| `docs/ai-nav/<模块路径>/_index.nav.md` | 仅当总索引不足以指导定位时补充，记录模块内部关键入口与修改线索 |

总索引使用简短表格即可：

```markdown
| 模块 | 职责 | 代码入口 | 相关文档 |
| --- | --- | --- | --- |
| 订单 | 创建订单与状态流转 | `src/orders/index.ts` | [订单设计](../orders.md) |
```

示例路径需替换为项目中已核实的路径。文档链接相对于所在 Markdown 文件解析；代码路径注明以项目根目录为基准。

模块详情只补充总索引无法表达的信息，例如公开入口、关键调用关系、业务规则所在位置、修改时需要联动的模块。引用已有设计文档，避免重复维护其内容。

默认不为每个源文件创建 `.nav.md`。已有逐文件导航保留，按本次变化维护相关内容；只有用户明确需要或复杂文件确有独立说明价值时才新增。

## 3. 保持内容有效

- 索引项目自有源码和影响业务行为的配置，跳过依赖、生成物、缓存及忽略文件；用户指定的文件单独处理。
- 记录稳定的模块路径和符号名，省去易过期的行号、文件计数和完整导出清单。
- 规则引用项目已有约定；从代码推断的模式标为观察结果，不自动升级为禁止事项。
- 若导航需要列出运行或验证命令，从当前项目配置核实。
- 模块职责、路径、公开入口或关键调用关系变化时更新对应条目；实现细节变化但定位信息未变时无需改文档。
- 文件移动或删除时修正受影响链接。保留手写说明；与源码冲突时指出依据并修正相关内容，不能整篇覆盖。

导航维护本身不执行暂存或提交；需要提交时遵循当前任务的提交范围。

## 4. 验收

核对本次新增或修改的路径、符号及链接是否有效，并从索引出发验证能找到所描述的实际实现。确认每个检查过的受影响模块都有对应更新，或有无需更新的依据。

交付时简要说明更新了哪些导航、覆盖哪些模块、做了什么核对，以及未覆盖的范围。以定位是否准确为完成标准，不以生成文档数量为标准。
