# 从零建立开发方式

在写首个业务功能前，明确采用什么开发方式，以及后续代码如何归属。下面的方案用于执行，不设置额外的“批准架构后才能开发”关卡；只有影响业务范围或重大技术约束且无法合理判断的信息需要询问。

## 1. 根据当前需求选择最小架构

先检查目录与项目约定，确认确实属于新项目，保护已有文件。依据已知需求说明：运行平台、关键用户流程、数据存储、身份与权限、外部集成、部署方式。区分已确认事实与暂定假设；只追问会改变架构或业务结果的未知项，不要求用户先回答完整访谈清单。

技术栈已有指定时沿用；未指定时给出一个符合约束的推荐方案及简短理由，包括框架、语言、存储和验证工具。使用当前官方资料核验会变化的版本、兼容性与接口，避免凭记忆拼接脚手架配置。

普通业务应用默认采用**按业务模块组织的单体架构**，保留框架规定的入口；只有当前存在明确的独立部署或隔离需求时才引入独立服务。简单工具、脚本或单页应用按实际复杂度缩小结构，不套用完整前后端分层。

开始实现前给出简短的项目方案：

| 项目 | 必须说清的内容 |
| --- | --- |
| 技术栈与运行方式 | 当前采用什么，为什么适合已知约束 |
| 业务模块 | 用业务名称划分职责，每项关键规则和数据由谁负责 |
| 通用能力 | 当前已知会共享的工具、基础设施与界面能力，以及具体使用场景 |
| 目录与依赖 | 入口、业务模块、公共能力实际放在哪里，允许怎样调用 |
| 首个功能 | 哪条用户操作可以贯通入口、规则、数据和结果，如何验收 |

完成标准：首批需求都能映射到明确的模块责任；不能只列框架名称和目录树。

## 2. 把开发约定留在项目里

在已有架构文档中维护上述方案；没有合适载体时写入 `docs/architecture.md`。内容保持精简：模块职责、当前公开入口、依赖规则、数据归属和关键选择理由。未来设想明确标为未实现，不把计划写成现有能力。

在项目 `AGENTS.md` 中加入简短入口，保留原有指令；下面是需按实际路径调整的示例：

> 新增功能、修改业务逻辑或调整模块接口前，读取 docs/architecture.md，核对模块归属、已有能力与依赖约定；有 modular-development 技能时加载它。新增代码按已记录的模块职责落位，共享能力变更检查现有调用方，接口或依赖规则变化同步文档。

项目架构文档要包含足够的本地约定，使没有安装该技能的开发者也能执行；不要只留下指向个人电脑绝对路径的链接。

完成标准：后续会话能通过项目入口找到实际开发约定，不必依赖起步会话的记忆。

## 3. 建立最小可运行骨架与边界

使用所选框架的标准脚手架并遵守其路由、构建与运行约定。按业务模块组织功能，模块内部随复杂度增长再分文件。以下只表示责任关系，不是所有项目必须复制的目录模板：

```text
src/
  app/                 # 框架入口、路由及跨模块流程组合
  modules/
    orders/            # 订单规则、数据操作、业务专用界面与公开能力
  shared/
    ui/                # 与具体业务无关的公共界面组件
    lib/               # 通用计算和转换
    infrastructure/    # 通用网络、存储等有副作用的能力
```

只有出现实际代码时才创建对应目录。全栈项目按框架要求保留客户端与服务端隔离，凭据和服务端数据访问不能通过共享目录进入客户端。后端项目不创建 UI 目录。

对第一批模块确定以下约定，并在首个功能中落实：

- 入口组织流程，业务模块拥有业务规则，公共能力服务于模块；公共能力不导入具体业务。
- 跨模块通过约定的公开接口协作，不直接读写对方内部状态或绕过其规则修改数据。真正需要的接口才实现。
- 每项关键状态与数据有明确归属；接口说明输入、输出、失败结果及副作用。按框架既有方式组织存储，不为假想的数据库替换创建空接口层。
- 明确当前使用的组件库及样式来源；同类基础交互沿用同一套能力。业务专用组件留在所属模块，暂未复用的组件不强制发布到公共层。

建立运行、构建和适用的类型或静态检查命令。利用所选工具链已有的导入限制、包可见性或模块机制表达能自动检查的边界，并接入现有检查入口。工具链无法直接表达时，先记录具体限制并核对首个功能的依赖；需要新增工具时说明它解决的实际缺口和成本，不自制一套解析器，也不声称已自动约束尚未实现的规则。

完成标准：骨架能启动，已有检查能运行，至少首个模块的代码归属与依赖约束能被核对；空文件夹和空接口不算实现。

## 4. 用首个完整功能证明架构可用

选择已确认需求中有代表性且范围小的用户流程，完成一次从输入到业务规则、数据操作和结果反馈的闭环。需要持久化的功能用真实配置的存储验证读回；临时内存或模拟服务只能报告为原型。

通过模块公开能力验证业务正常、边界和失败行为；有 UI 时在实际浏览器中验证完整操作。检查入口没有重复业务规则、公共层没有反向依赖、客户端与服务端职责没有混用。若结构导致无价值的转发或复杂参数，先简化再把它作为后续范例。

完成标准：首个功能可操作，关键行为有验证结果，架构文档与实际路径一致，检查覆盖和缺口有明确说明。后续功能按主技能流程逐个增加，保持同一套约定；不要先横向铺满所有页面和空服务再接业务逻辑。
